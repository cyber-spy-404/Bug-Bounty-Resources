# 📁 Django Framework — Security Review & Audit Guide

*Contributed by Cyber_Spy.404 | Educational Bug Bounty Series*

> **Scope and ethics:** Testing Django web applications requires understanding framework-specific conventions and security middlewares. Conduct all tests within approved program scopes. **Do not use disclosed debug credentials or secret keys to forge administrative sessions or access production databases.** Report configuration exposures immediately.

---

## 📌 Executive Summary

**Django** is a high-level Python web framework designed with a "batteries-included" security model. Out of the box, Django includes built-in mitigations against SQL Injection, CSRF, Clickjacking, and Cross-Site Scripting.

However, deployment misconfigurations (such as enabling `DEBUG` in production, wildcard `ALLOWED_HOSTS`, exposing `SECRET_KEY`, or misusing raw ORM queries) frequently bypass Django's defensive architecture, leading to critical vulnerabilities.

```
+---------------------------------------------------------------------------------+
|                        Django Security Review Vectors                           |
+---------------------------------------------------------------------------------+
        |                                |                                 |
        v                                v                                 v
  DEBUG Mode Enabled             SECRET_KEY Exposure              ORM / Raw SQL Flaws
  - Full traceback pages         - Session forgery via signing    - .extra() SQL injection
  - Environment variables leak   - Password reset token forgery   - Raw SQL concatenation
```

## 🔍 Core Django Misconfigurations & Vulnerabilities

### 1. `DEBUG = True` Enabled in Production
When `DEBUG = True` is active in `settings.py`, any unhandled exception (triggered by sending a 404 URL or invalid parameter types) renders Django's interactive technical traceback page.

#### Disclosed Information Includes:
- **`SECRET_KEY`:** The cryptographic master key for the entire application.
- **Database Connection Strings:** Hostname, username, and plaintext password in `DATABASES`.
- **API Keys & Cloud Secrets:** AWS tokens, Stripe keys, SendGrid secrets in `settings`.
- **Complete Framework Environment:** Python version, installed packages, internal file paths.
- **Source Code Snippets:** 10–20 lines of server-side Python source code surrounding the error.

#### Safe Detection:
Send a request to a non-existent URL (e.g., `GET /random-404-check-9921`). If the response displays the yellow Django debug error page ("Page not found at /... (Django Version X.Y.Z)"), `DEBUG = True` is confirmed.

---

### 2. `SECRET_KEY` Compromise & Exploitation
The Django `SECRET_KEY` is used for all cryptographic signing across the framework:
1. **Session Cookie Forgery:** If using signed cookie sessions (`django.contrib.sessions.backends.signed_cookies`), knowing the `SECRET_KEY` allows an attacker to forge session cookies with arbitrary `user_id` values.
2. **Password Reset Token Forgery:** Tokens generated by `PasswordResetTokenGenerator` incorporate the `SECRET_KEY`.
3. **Cryptographic Signing (`django.core.signing`):** Any signed token used for email verification, unsubscribe links, or state parameters can be forged.

---

### 3. Wildcard `ALLOWED_HOSTS` Configuration
If developers configure:
```python
# ❌ VULNERABLE: Disables Host header validation
ALLOWED_HOSTS = ['*']
```
Django allows any client-supplied `Host` header to pass to views. This directly enables:
- **Password Reset Poisoning:** If password reset emails use `request.get_host()`.
- **Web Cache Poisoning:** If an upstream caching reverse proxy uses the Host header.

---

### 4. Django ORM SQL Injection Risks
While Django's QuerySet API (`.filter()`, `.get()`) automatically parameterizes queries, developers can introduce SQL injection through raw query APIs:

#### Vulnerable ORM Patterns:
- **`extra()` Clause Concatenation:**
  ```python
  # ❌ VULNERABLE: Concatenation inside extra()
  User.objects.extra(where=[f"username = '{user_input}'"])
  ```
- **`raw()` SQL Concatenation:**
  ```python
  # ❌ VULNERABLE
  User.objects.raw(f"SELECT * FROM myapp_user WHERE name = '{user_input}'")
  
  # ✅ SECURE: Parameterized
  User.objects.raw("SELECT * FROM myapp_user WHERE name = %s", [user_input])
  ```
- **Column / Order By Injection:** Passing untrusted strings to `.order_by(user_input)` on older Django versions.

---

### 5. Disabled Security Middlewares
Inspect responses to verify that Django's standard security middleware chain is active:
- **Missing `CsrfViewMiddleware`:** State-changing POST requests succeed without `csrfmiddlewaretoken`.
- **Missing `XFrameOptionsMiddleware`:** Absence of `X-Frame-Options: DENY` allows Clickjacking.
- **Missing `SecurityMiddleware`:** HSTS (`Strict-Transport-Security`) headers and `X-Content-Type-Options: nosniff` are omitted.

## 🛡️ Production Hardening Checklist for Django

### 1. Disable Debug Mode
```python
# settings.py
DEBUG = False
```

### 2. Configure Strict `ALLOWED_HOSTS`
```python
ALLOWED_HOSTS = ['example.com', 'www.example.com']
```

### 3. Secure Cookie & Session Settings
```python
SESSION_COOKIE_SECURE = True
SESSION_COOKIE_HTTPONLY = True
SESSION_COOKIE_SAMESITE = 'Lax'
CSRF_COOKIE_SECURE = True
CSRF_COOKIE_HTTPONLY = True
CSRF_COOKIE_SAMESITE = 'Lax'
```

### 4. Enable Complete Security Middlewares
```python
MIDDLEWARE = [
    'django.middleware.security.SecurityMiddleware',
    'django.contrib.sessions.middleware.SessionMiddleware',
    'django.middleware.common.CommonMiddleware',
    'django.middleware.csrf.CsrfViewMiddleware',
    'django.contrib.auth.middleware.AuthenticationMiddleware',
    'django.contrib.messages.middleware.MessageMiddleware',
    'django.middleware.clickjacking.XFrameOptionsMiddleware',
]

SECURE_HSTS_SECONDS = 31536000
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SECURE_HSTS_PRELOAD = True
SECURE_CONTENT_TYPE_NOSNIFF = True
X_FRAME_OPTIONS = 'DENY'
```

### 5. Run Django's Built-in Deployment Check
Before deploying, always execute:
```bash
python manage.py check --deploy
```
